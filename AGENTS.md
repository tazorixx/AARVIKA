# AARVIKA — Codex project rules (APP FIRST version)

These instructions supersede any earlier AARVIKA handoff *development-order* guidance. Preserve relevant existing root `AGENTS.md` rules; reconcile before merging.

1. **Build the complete NEW customer Android/iOS application first.** Every confirmed department — Wedding, Birthday, Personalized Gifts, Anniversary, Hampers, Clothing, Stationery, Furniture — must be working and tested on staging before modifying the existing admin. Ninth category remains unconfirmed and inactive.
2. **Read** `AARVIKA_FULL_APP_FIRST_MASTER.md`, the matching task file, original category PDFs/images, and relevant existing repo source before code changes. Full actual repository is required; the `13scripts` archive is partial, and admin source can only be inspected read-only until the app-ready gate.
3. Scope each task carefully. Propose touched paths, data-contract changes, tests and rollback first. Do not create giant rewrites or mix UI redesign, database migration and admin modification in one task. No silent production deployment.
4. Mobile brand: temporary AARVIKA, purple `#62298E`, dark plum `#3E155C`, restrained lavender/pink/peach/mint/cream support. Compact accessible fonts/cards/grids, consistent reusable components, responsive layout, smooth light animation, reduced motion, no oversized AI-template cards.
5. Five shared tabs: Home, Categories, Offers, Wishlist, Account. Cart in header. Common search/header across discovery pages; category-specific browse facets and PDP details are NOT deleted for consistency.
6. Source PDF's three-level catalogue (Main → Sub → Child) and exact Hampers (10), Stationery (11), Personalized (9) families; Clothing's 8 browsing columns; Furniture's 9 Home + 9 Commercial; Wedding traditions/functions; Birthday and Anniversary recipient, budget, interest/milestone/delivery paths. Use source files for complete child labels.
7. One product / one SKU stock authority / multiple categories & collections. Separately model occasion, culture, region, ceremony, recipient and homepage placements. No duplicate products in separate department collections; no fake live inventory, ratings, discounts or shipping ETAs.
8. Before admin exists, use fixture adapters for visual work and isolated staging backend with **demo-labelled seed data** for full functionality. All components and category sections must consume typed contracts so admin later changes data without rewriting app layouts.
9. Payment/security: server-authoritative SKU price, stock, tax/discount, payment verification and order state. Test gateway only in staging; fake payment only when explicitly labelled simulation. Quote-only products have inquiry action, not a fake payment action. Auth, privacy/uploads, Firestore rules and idempotent checkout are required.
10. Treat all eight departments as required release scope. No dead buttons or 'coming soon' as substitute for completion. Special flows (wedding combo, birthday age, personalization preview/upload, anniversaries, hamper builder, apparel variants/size, stationery specs, furniture quote) must work.
11. Test real device/simulator viewports, slow network, missing product, out of stock, keyboard, reduced motion, accessibility, auth failure, variant/cart states and payment fail/retry. State actual commands and outcomes; do not invent successful tests.
12. **HOLD EXISTING ADMIN:** No changes to its code, Firestore schema/data, auth roles, homepage builder or deployments until Task 11 app-ready gate is approved. Only Task 12 onward may update admin, using additive backward-compatible changes with dry-run/rollback and staging verification.
13. Existing admin code/parser issues in reference audit must be verified against full repository at that later stage; preserve working admin and historical records. Website is Task 14 and uses the same catalogue/business logic.
14. Every task response: (a) what was inspected, (b) planned and changed files, (c) how it looks/works, (d) tests and exact results, (e) remaining gaps and next task. Stop at end of assigned scope.
